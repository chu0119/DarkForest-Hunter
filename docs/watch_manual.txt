└──────────────────────────────────────────────────────────────────────────────┘

    python run.py watch

  · 7×24 挂机持续扫描，5 个数据源并行，后台验证查余额，TUI 面板实时显示。
  · 代理全自动（config.ini > 环境变量 > 自动探测本地 Clash > 直连），不用敲 --proxy。
  · Ctrl+C 优雅退出（自动排空验证队列 + 刷盘）。
  · 想立刻看到所有有效 key（含 ¥0）进 CSV：  python run.py watch --min-balance 0


┌──────────────────────────────────────────────────────────────────────────────┐
│  1. 它是什么 / 适合什么场景                                                   │
└──────────────────────────────────────────────────────────────────────────────┘

  watch 是“持续监控”模式：长时间挂着，不断从公开代码源里找泄露的 AI API key，
  验证有效性、查余额，把高价值的记下来。它是本项目唯一的扫描入口：

    - watch : 一直循环跑，跨天累积，带 TUI 面板，适合挂服务器/本机后台。
              裸启动 `python run.py` 等价于 watch。

  适合：
    · 长期监控新泄露（时间切片优先抓最近提交）。
    · 攒一批高价值 key 做安全研究。
    · 看“哪些查询模式最出 key”（query_stats.json 会自己学）。


┌──────────────────────────────────────────────────────────────────────────────┐
│  2. 架构（看懂行为的关键）                                                    │
└──────────────────────────────────────────────────────────────────────────────┘

  生产者-消费者 + TUI 三层：

    ┌─────────────┐   每个 source 一个线程，独立循环
    │ 扫描端(生产) │   扫到 key → submit 到验证队列
    │ 5 个数据源   │   github_search 连续跑满 ~9次/分钟(10/min/token 硬上限)
    └──────┬──────┘   其余源按 --interval 间隔轮次
           │ 发现 key
           ▼
    ┌─────────────┐   N 个 worker 线程(默认4)，从队列取 key
    │ 验证broker  │   多平台统一验证（默认 GET-only，不消耗配额）
    │ (消费者)    │   有效结果写入内存 _results + SQLite
    └──────┬──────┘
           │ 验证完
           ▼
    ┌─────────────┐   主线程 2fps 刷新面板；定期把高价值 key 写 CSV/state
    │ TUI 面板    │   Ctrl+C → 排空队列 → final_save 刷盘
    └─────────────┘

  关键点：
    - 扫描和验证完全并行：扫描不等验证，验证不阻塞扫描。
    - 去重三层：内存 _seen（同次运行）+ 启动种子（SQLite known_keys ∪ watch_state.json，
      重启后不重复验证历史 key）+ CSV 增量账本。
    - github_search 的速度天花板是 GitHub Code Search 的 10次/分钟/token，
      和 token 数成正比（1 个 token ≈ 9~10 次/分钟）。


┌──────────────────────────────────────────────────────────────────────────────┐
│  3. 数据源（默认 5 个）                                                       │
└──────────────────────────────────────────────────────────────────────────────┘

  默认并行扫描这些源（DEFAULT_WATCH_SOURCES）：

    github_search   GitHub Code Search（主力，155条查询轮转，连续跑满预算）
    github_commits  最近提交 diff（新鲜度高，窗口可配）
    github_events   PushEvent 实时流
    gitlab          GitLab
    npm             npm 注册表

  注：Gitee/PyPI/Docker 等历史低产出或未实现源不再写入默认目录。
  可用 --sources 自定义（见第 6 节）。更多可用源名见  python run.py --list-sources 。


┌──────────────────────────────────────────────────────────────────────────────┐
│  4. 全部命令行参数                                                            │
└──────────────────────────────────────────────────────────────────────────────┘

  ── 公共参数（所有子命令都有，watch 也支持）─────────────────────────────────

    --proxy URL        手动指定代理。一般不用填——会自动解析（见第 5 节）。
    --concurrency N    扫描并发数（默认 15，来自 config.ini [deepseek] concurrency）。
    --verbose          控制台输出 DEBUG 级诊断（限流/网络错误细节）。
    --log-file PATH    把 DEBUG 级诊断轨迹写到文件（排障用）。

  ── watch 专属参数 ─────────────────────────────────────────────────────────

    --interval N       非github源的轮次间隔秒数（默认 300=5分钟）。
                       注意：github_search 忽略此项，它自己连续跑（rest=0）。
                       调小→外部源扫更勤（但可能撞它们的限流）；调大→更省资源。

    --min-balance X    CSV 记录的余额阈值(¥)，默认 1.0。
                       只有 balance_cny > 此值的 key 才进 watch_high_value.csv。
                       想看到所有有效 key（哪怕 ¥0）： --min-balance 0

    --sources A B C    自定义数据源列表（覆盖默认 5 源）。
                       例: --sources github_search huggingface gitlab
                       注：github_search 已在默认源里，--include-github 是遗留开关，
                           现在基本是 no-op。

    --include-github   遗留开关（github_search 默认已启用）。一般不用管。

    --once             只跑一轮就退（测试用）。外部源立即扫描；
                       退出会等待在途验证（至少 120s）。

    --shutdown-timeout S  退出时等待在途验证秒数（默认 30）。
                          --once 会自动抬升到至少 120s。

    --verify-interval S  验证 worker 每次请求间隔秒数（默认 0.5）。
                         单 worker QPS ≈ 1/S。
    --verify-workers N   验证 worker 线程数（默认 4）。
                         总验证吞吐 ≈ N / S（默认 4/0.5 = 8 次/秒 ≈ 480/分钟）。
                         队列“待验”一直涨就调大 N；别太猛，DeepSeek 会 reset 连接。

    --github-pages N   github_search 每条查询取的页数（默认 1）。
                       1 = 快轮次、广覆盖（推荐 24/7）。
                       2 = 每查询挖更深，更全但调用翻倍、轮次慢一倍。


┌──────────────────────────────────────────────────────────────────────────────┐
│  5. 代理（全自动 + 回退）                                                     │
└──────────────────────────────────────────────────────────────────────────────┘

  解析顺序（取第一个非空）：
    1. 命令行 --proxy
    2. config.ini [proxy] url
    3. 环境变量 HTTP_PROXY / http_proxy
    4. 自动探测本地端口：7897(Clash) / 10809(V2Ray) / 7890 / 10808 / 1080 / 8080
    5. 都没有 → 直连

  回退机制：
    · 选定代理后会探活（打一下 api.github.com 看通不通）。
    · 不通 → 自动降级为直连，并打告警日志。
    · 所以三种情况都 OK：Clash 开着 / Clash 没开 / 连 config 都没填。

  建议：把代理写进 config.ini 一劳永逸：
        [proxy]
        url = http://127.0.0.1:7897


┌──────────────────────────────────────────────────────────────────────────────┐
│  6. 常用启动方式（复制即用）                                                  │
└──────────────────────────────────────────────────────────────────────────────┘

  # 标准挂机（最常用）
  python run.py watch

  # 想立刻看到所有有效 key（含 ¥0）进 CSV，验证 watch 在出 key
  python run.py watch --min-balance 0

  # 榨干单 token：github_search 挖 2 页（更全，但每轮慢一倍）
  python run.py watch --github-pages 2

  # 验证队列总在涨（“待验”数字不降），加验证并发
  python run.py watch --verify-workers 6

  # 排障：打开 DEBUG 诊断 + 落盘
  python run.py watch --verbose --log-file results/diag.log

  # 只跑一轮（快速验证能不能跑通）
  python run.py watch --once

  # 只扫指定几个源
  python run.py watch --sources github_search huggingface gitlab


┌──────────────────────────────────────────────────────────────────────────────┐
│  7. github_search 的扫描智能（本轮优化的核心）                                │
└──────────────────────────────────────────────────────────────────────────────┘

  这是主力源，单 token 下被 10次/分钟 限流，所以要把每次调用榨干：

    [连续扫描]   不再“扫5分钟歇5分钟”，改为连跑 → 调用量 ~2×（消除空转）。
    [收益优先]   每条查询记命中率(hits/runs)；每轮按收益排序，高产的先跑；
                 长期 0 命中的（如裸 "deepseek sk-"）自动跳过(is_barren)。
                 实测：filename:java≈38key/调用、filename:env≈9、裸查询≈0。
    [查询变异]   从历史 TOP 收益查询自动派生变体（每轮≤5条）：
                   - 加 NOT test / NOT example 降噪
                   - filename 近邻簇：java↔kt↔scala、py→ipynb、js↔ts、yml↔yaml
                   - 变量后缀互换：_API_KEY↔_KEY↔_TOKEN
                 变体命中→记为高产、长期保留并继续变异；0命中→自动跳过。自调节。
    [时间切片]   每轮注入最近 1d/3d/7d/30d 的 pushed:> 窗口查询，优先抓新泄露。
    [分桶轮转]   155 条静态查询分 4 桶，每轮跑 1 桶，循环覆盖。
    [历史补扫]   每 10 轮插一次 30–90 天前的老提交查询。

  限流节流：per-token pacing 6.5s/调用（≈9次/分钟，安全余量 < 10次/分钟）。
            正常窗口轮转(短等待)静默；只有 ≥20s 的真实长等待才告警。


┌──────────────────────────────────────────────────────────────────────────────┐
│  8. 验证（先只读 GET，再最小探测确认）                                        │
└──────────────────────────────────────────────────────────────────────────────┘

    验证方式：先 GET models/balance（只读，不消耗配额）；通过后补一次
    max_tokens=1 的 /chat/completions 最小探测确认"实际可用"（微额消耗，
    默认开——实测口径校准：余额接口显示 ≠ 实际可调用）。
    --no-allow-chat-probe 或 [verification] allow_chat_probe=false 可关回纯只读。
    例外平台：魔搭/NVIDIA/LongCat 的 /models 公开不鉴权（假 key 也 200），
    只读无法判定——默认兜底发一次最小探测
    （probe_unclear_platforms=false 或 --no-probe-unclear 可关闭，关闭后判 error）。
    状态：200 有效、401 无效、402 有效但欠费、429 限流、其余错误。
    吞吐：≈ verify-workers / verify-interval （默认 8 次/秒）。
    国内直连：DeepSeek 是国内 API，验证默认不走代理（避免代理 IP 被风控）。


┌──────────────────────────────────────────────────────────────────────────────┐
│  9. 输出文件（都在 results/ 下）                                              │
└──────────────────────────────────────────────────────────────────────────────┘

  watch_high_value.csv   高价值 key 的【增量账本】（核心战果）：
                         - 余额(¥) > --min-balance 的 key 才进。
                         - 增量：已有行不覆盖，新高价值 key 追加。
                         - 仅当某 key 被验证为【欠费】(balance_cny<0) 才删除该行。
                         - 按余额降序，含首次发现/最后验证时间。

  watch_state.json       当前所有【有效】key 的快照（仅有效，不含无效，防长跑膨胀）。
                         最多每 15s 重写一次（节流）；退出时强制刷盘。
                         【保存=合并】：每次重写 = 本次验证结果 ∪ 磁盘历史，
                         重启后首轮保存不会清掉上次会话的 key（新验证覆盖同名 key，
                         纯历史 key 原样保留）。
                         **注意：这是视图，CSV/db 才是账本——万一它被清空，
                         先查 watch_high_value.csv 和 darkforest.db（历史仍在）。**

  darkforest.db          SQLite 全量历史 + 跨运行去重种子（schema 见 store.py）。
                         每个 key（含无效）都 upsert，用于下次启动时 _seen 预填去重。
                         连接在主线程创建、worker 线程写入（check_same_thread=False，
                         写入串行化 + 失败记日志——不会静默丢历史）。
                         可用 sqlite3 直接查：select * from keys order by balance desc;

  watch_state.json       另一个启动种子：重启时与 SQLite 一起预填 _seen（互为备份），
                         历史 key 不重复验证；高价值 key（>阈值）直接回显到 TUI 表格。

  query_stats.json       github_search 查询收益学习（hits/runs/last_hit）。
                         变异引擎据此派生变体；可看哪些查询肥、哪些被标 barren。

  watch_session_*.log    本次会话的日志文件（每次启动一个，带时间戳）。


┌──────────────────────────────────────────────────────────────────────────────┐
│  10. TUI 面板（6 层，2fps 刷新）                                              │
└──────────────────────────────────────────────────────────────────────────────┘

    标题栏    🌲 DARKFOREST WATCH · 活跃源数 · 已运行时长 · 高价值 key 数
    统计卡片  5 个：提交 / 待验 / 有效 / 💰高价值 / 总值(¥)
    验证条    [████░░] 进度% · ✓已验/提交 · 待验 · 有效 · 速率/分钟 · ETA
    数据源    每源一行状态：⣾扫 / 😴休 / ✓完 / ⏭跳 + 轮次R# + 发现数
    高价值表  余额最高的 key 列表：完整key + 余额(色阶) + 来源/文件 + 验证时间
    日志      最新 10 条，按级别着色（❌错 ⚠️警 ✅成 •信息）


┌──────────────────────────────────────────────────────────────────────────────┐
│  11. 启动 / 停止                                                              │
└──────────────────────────────────────────────────────────────────────────────┘

  启动：  python run.py watch
  停止：  Ctrl+C
          → 设置退出标志 → 等扫描线程退出 → 排空验证队列(最多60s) → final_save 刷盘
          → 打印运行总结（时长/提交/验证/高价值/各源统计）
          → 再按一次 Ctrl+C 强制退出（不等排空）

  24/7 挂机建议：
    · 用 nohup / tmux / Windows 任务计划常驻。
    · 崩溃/重启不丢：SQLite 全量留存，下次启动自动去重种子。


┌──────────────────────────────────────────────────────────────────────────────┐
│  12. 调参指南：怎么抓更多                                                    │
└──────────────────────────────────────────────────────────────────────────────┘

  目标“抓尽可能多”，按收益排序的旋钮：

    1) 多 GitHub token（最大杠杆，~N× 吞吐）
       config.ini [github] token = ghp_xxx,ghp_yyy,ghp_zzz   （逗号分隔）
       每个 token 独立 10次/分钟。1个token是天花板，加 token 才能真提速。
       （注意：同账号多 PAT 可能共享配额，最好不同账号。）

    2) --github-pages 2     高产查询挖第 2 页，更全（调用翻倍，轮次慢一倍）。

    3) --verify-workers 6   验证跟不上扫描时加（“待验”不降就是跟不上）。

    4) --min-balance 0      想看全部有效 key 而不是只看正余额的。

    5) --interval 180       让外部源（非github）扫更勤（注意它们的限流）。


┌──────────────────────────────────────────────────────────────────────────────┐
│  13. 多久能看到收益                                                           │
└──────────────────────────────────────────────────────────────────────────────┘

    秒级        TUI“提交”计数涨（github_search 第一个调用 ~7s 回 ~10-38 个原始 key）
    1~2 分钟    TUI“有效”计数涨；darkforest.db / watch_state.json 开始落有效 key
    CSV 出现正余额 key   看运气——多数泄露 key 余额是 ¥0（被扫光/免费额度用完），
                       正余额的是少数。可能几分钟到一个，也可能跑半天才有。
                       这是真实分布，优化只提高“扫到有效 key”的速率，改不了余额分布。

  结论：有效 key 很快就有（看 TUI 计数器）；正余额 key 是概率事件。
        想立刻看到活动反馈，用 --min-balance 0 让 ¥0 的也进 CSV。


┌──────────────────────────────────────────────────────────────────────────────┐
│  14. 排障                                                                     │
└──────────────────────────────────────────────────────────────────────────────┘

  Q: github_search 很慢 / 一直“扫”
  A: 这是正常的——单 token 被限在 ~9次/分钟，一轮 ~45 调用 ≈ 5 分钟。
     想快：① config.ini 多填几个 GitHub token；② --github-pages 1（默认就是）。

  Q: 启动就提示“仅 N 个 GitHub Token…偏慢”
  A: 正常提示。1 个 token = 10次/分钟上限。多填 token 可 N× 提速。

  Q: “待验”队列一直涨不降
  A: 验证跟不上扫描。调大 --verify-workers（如 6~8），或 --verify-interval 0.3。

  Q: 跑半天 CSV 还是空的
  A: 默认 CSV 只收 balance>¥1 的。多数 key 余额 ¥0 不进 CSV。
     ① 加 --min-balance 0 看全部有效 key；② 看 darkforest.db 里有效 key 数。

  Q: 代理 / 网络错误刷屏
  A: 代理挂了会自动回退直连。用 --verbose --log-file results/diag.log 抓详情。
     确认 config.ini [proxy] url 对，或 Clash 在跑。

  Q: Ctrl+C 后好像卡住
  A: 在排空验证队列（最多60s，等在途的 429 退避完成）。再按一次 Ctrl+C 强退。

  Q: 重启后重复验证已知 key
  A: 不会。SQLite known_keys ∪ watch_state.json 启动时预填 _seen，已知 key 直接跳过验证。
     高价值 key 也会从上次会话回显到 TUI 表格（重启不空白）。

  Q: “提交”卡片突然从大数字掉回 0 / 重启后计数归零
  A: 已修复（2026-08-08）。该卡片现在是【累计】值：全程单调递增，轮次交替不再骤降；
     重启后从上次会话的提交量继续涨（历史 key 播种 _seen，不重验）。
     若仍异常：① 确认在最新代码上跑；② 看 results/watch_session_*.log 里
     “加载历史: N 个已验 key”一行是否出现。

  Q: 高价值表里“验证时间”列空白或显示奇怪字符
  A: 已修复（2026-08-08）。时间列应显示 HH:MM:SS（如 07:16:47）；
     曾误取单字符导致恒显示 "0"。


┌──────────────────────────────────────────────────────────────────────────────┐
│  15. config.ini 相关配置（可省掉命令行参数）                                  │

  [proxy]
  url = http://127.0.0.1:7897            # 代理地址（留空=直连/自动探测）

  interval = 300                          # = --interval
  min_balance = 1.0                       # = --min-balance
  verify_interval = 0.5                   # = --verify-interval
  verify_workers = 4                      # = --verify-workers
  concurrency = 15                        # = --concurrency
  include_github = false
  # sources = github_search huggingface gitlab   # = --sources（空格分隔）

  [github]
  token = ghp_xxx,ghp_yyy                 # 多 token 逗号分隔（提速最大杠杆）

  [deepseek]
  concurrency = 15                        # 公共 --concurrency 默认值

  config.ini 已被 .gitignore 排除，不会上传。首次用复制 config.ini.example 改。
